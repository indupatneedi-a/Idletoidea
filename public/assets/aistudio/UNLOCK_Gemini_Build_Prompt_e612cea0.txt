## 1. PRODUCT OVERVIEW

UNLOCK is a trusted shared-resource platform for makerspaces, innovation centres and similar institutions. Owners list underused equipment and spaces with clear eligibility and usage rules. Requesters (students from different colleges, independent inventors, startups, project teams) discover resources, check eligibility, request access, and follow the request to completion. Supervisors verify training and record condition. Administrators oversee owners, escalations and the audit log.

It is NOT an ordinary booking calendar. Its value is the combination of: discovery, risk-based eligibility checks, human approval, conflict-safe booking, fair allocation (booking caps and an explainable waitlist), before-and-after condition records, incident handling with human review, and a complete auditable history.

Scope decision: one institution for now (a fictional 'Demo Innovation Lab'), but every record carries organisationId and facilityId so more organisations can be added later.

## 2. NON-NEGOTIABLE RULES
- Pending is never shown as confirmed. A request becomes a confirmed booking only after all checks pass and, where required, an authorised human approves.
- Safety and eligibility are prerequisites, never ranking factors. A user without completed required training never gets access.
- Important decisions (restricted access, incident findings, damage responsibility, restrictions, penalties) are always made by an authorised person. AI never decides.
- An incident report is an allegation until reviewed. Never assign blame automatically because someone was the last user.
- No automatic financial penalties. Fees are simulated and labelled.
- Permission checks and state transitions run inside a single service layer (section 8), never only in the UI. Hiding a button is not security.
- Every important action is written to an append-only audit log with actor, role, time and reason.
- Payment state is independent of booking or transfer state. Permanent transfers (giveaway, sale) never use temporary booking or return states.
- Use only fictional data. Collect no real ID numbers, real payment details or sensitive documents.

## 9. STATE MACHINES
- Temporary request/booking: draft -> pending-review -> confirmed -> in-use -> returned. Side exits: rejected, cancelled, expired, waitlisted -> offered -> confirmed, overdue (from in-use). Only valid transitions are allowed; reject anything else.
- Auto-confirm path: pending-review -> confirmed immediately only when the resource is low risk AND the owner enabled auto-confirm AND eligibility, cap and overlap checks all pass.
- Permanent transfer (giveaway or sale): requested -> owner-confirmed -> handover-recorded -> transfer-complete (or rejected or cancelled). Never uses in-use, returned or overdue.
- Payment (separate): not-required, pending, marked-as-paid (requester claim, unverified), cancelled, refunded-simulated. Payment state never completes a booking by itself.
- Waitlist: waiting -> offered (timed) -> accepted, or expired (offer passes to the next eligible person).
- Incident: open -> awaiting-response -> under-review -> resolved (human decision with rationale). Serious or contested cases can be escalated to admin.
- Owner verification: self-registered -> spot-checked, with flagged and suspended as side states.

## 10. BUSINESS RULES

10.1 Risk-based eligibility
- Low risk: account check plus acknowledging rules; may auto-confirm if the owner enabled it.
- Medium risk: safety quiz passed; owner policy decides whether review is needed.
- High risk: quiz passed AND an authorised supervisor approves eligibility before any booking can be confirmed.
- Eligibility is shown to the requester as a checklist with 'Met' or 'Not met' and what to do next. Approvals expire after 12 months or if safety requirements change. Label all verification 'Demo verified' or 'Simulated verification'.

10.2 Fair allocation
- Order of decisions: (1) eligibility and safety, (2) the user's active booking cap for that resource, (3) slot availability, (4) approval, otherwise (5) waitlist.
- Cap: owner-set per resource; default 2 active (future or in-use) bookings per user for high-demand resources. The cap, waitlist rule and tie-breaker are published on the listing.
- Waitlist: ordered by the timestamp the user became eligible and joined, tie-breaker is request id. One entry per user per resource. Spots are not transferable. A user at their cap cannot join. Leaving and rejoining goes to the back.
- When a slot frees up, offer it to the first eligible waitlisted user for the offer window (default 24 hours); re-check eligibility and cap at offer time; if not accepted, pass to the next person without penalising the first.
- Rules are never changed retroactively after seeing who requested. Changes apply to future requests only and are logged.
- Every allocation decision is logged with the rule applied.

10.3 Decision explanations (reason codes shown to the user)
- APPROVED_ELIGIBLE, REJECTED_TRAINING_INCOMPLETE, REJECTED_SLOT_UNAVAILABLE, REJECTED_CAP_REACHED, REJECTED_MAINTENANCE, REJECTED_OWNER_DECLINED (owner note required), WAITLISTED_FIRST_ELIGIBLE (show position and the rule), NEEDS_MORE_INFO (question and deadline), EXPIRED_NO_REVIEW, RESTRICTED_OVERDUE.
- Every approval, rejection and waitlist placement shows a plain-language reason and a link to the published rule used. The same record appears in the timeline and audit log.

10.4 Conflicts and competing requests
- Overlap prevention: the confirm step and the slot write happen in one transaction. Two confirmed bookings can never overlap on the same resource. Test this explicitly.
- Competing pending requests for one slot: the first eligible request is reviewed first; others stay pending or move to the waitlist with an explanation. Approving one never silently rejects another.
- If an owner blocks a slot after confirmation (maintenance or internal use): notify the affected user, offer alternative slots or resources, give priority on the next matching slot, and log the reason.
- Pending requests expire after the owner-set time (default 48 hours) and the requester is notified.

10.5 Cancellations and no-shows
- Owner-defined per listing: cancellation notice period, simulated cancellation fee, no-show definition, consequence of repeated no-shows. Show these on the listing page and again on the booking confirmation.
- Cancelling records timely or late, frees the slot, and offers it to the first eligible waitlisted user. Owner and waitlisted user are notified.
- Owners or supervisors record no-shows. Repeated no-shows only raise a flag for review; nothing is penalised automatically. Emergencies and disputes go to human review and the user can add an explanation.

10.6 Extensions
- A requester asks before the booking ends. Allowed only if the next slot is free, nobody is waitlisted for it, and the user has no overdue items.
- Auto-extend only for low-risk resources where the owner enabled it, once, up to the original length or maxExtensionMinutes. Otherwise the owner or supervisor decides with a reason.
- If a waitlist exists the extension is refused with an explanation. A booking already overdue cannot be extended. Extra simulated charges are recorded separately.

10.7 Overdue returns
- Stage 1: reminder shortly before and at the due time. Stage 2: when not returned, mark Overdue and notify requester and owner. Stage 3: configurable grace period. Stage 4: after the grace period, temporarily restrict the user from new temporary bookings until the item is returned or an owner or supervisor reviews the case. Stage 5: resolution, restriction lifted, outcome logged.
- Users can report an emergency or dispute the return record. Staff review exceptions. No automatic financial penalties. Every change is logged.

10.8 Repeated-problem flags (rule-based, not AI)
- Count late returns, no-shows, late cancellations and incidents naming the user. When an owner-set threshold is passed, show a flag in the owner or supervisor queue. A flag only prompts review and never restricts a user on its own.

10.9 Permanent transfers and payments
- Giveaway and sale have their own handover flow: request, owner confirms recipient, handover recorded, transfer complete. Record only a simulated payment state for sales.
- Payment simulation is labelled everywhere: 'Simulation only. No real money is moved.' Show the separate payment status chip next to the booking status.

## 12. GEMINI AI FEATURES (EXACTLY TWO)

12.1 'Find my match' (used on the Discovery page)
- Input: a free-text project description plus optional budget, location and date needs.
- Pre-filter in code first: only send resources that are active, within the budget, and where the user's eligibility status is not blocked, together with each resource's id, title, category, price, location, riskLevel and next availability. The AI can only rank options that already pass these checks and can never override eligibility, safety, availability or published allocation rules.
- Ask Gemini to return strict JSON: an ordered array of {resourceId, reason} using only the supplied ids. Validate the JSON; discard unknown ids; show up to 3 results with the reason and an 'AI suggested' label. Always show the standard rules and eligibility checklist on the resource page.
- Fallback: if the AI call fails or returns invalid JSON, run keyword and filter matching and show 'AI unavailable, showing keyword matches'.

12.2 'Summarise this incident' (used on the Incident review screen)
- Input: the report text, timeline events, condition records and any response, with names replaced by roles (Requester, Owner, Supervisor) and no emails or contact details.
- Ask Gemini for neutral JSON: {reportedAllegations: [], verifiedFacts: [], missingInformation: [], timeline: []}. Facts may only come from system records (timestamps, condition records). Allegations come from the report text. The model must not invent missing details, must not state fault or liability, and must not suggest penalties.
- Show the result in a panel labelled 'AI-generated summary. Advisory only.' The reviewer can edit it before saving. The decision form stays fully manual.
- Fallback: if AI is unavailable, show the original report and records in full with 'Summary unavailable'.

12.3 Guardrails
- Never use AI for approvals, rejections, waitlist order, eligibility, penalties or damage responsibility. Never send personal contact data. Label all AI output. Handle errors, timeouts and rate limits gracefully.
